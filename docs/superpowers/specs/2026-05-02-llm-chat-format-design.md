# LLM-чат: формат и место в продукте

**Дата:** 2026-05-02
**Статус:** design (брейншторм закрыт, ждёт plan)
**Затрагиваемые модули:** новый `lib-modules/assistant/`, `lib-modules/content-editor/`, `lib-modules/app-layout/`

## Контекст и проблема

Сейчас LLM-чат живёт исключительно внутри редактора поста (`lib-modules/content-editor/components/EditorChatPanel.vue`). Создать новый диалог нельзя, чат всегда привязан к посту через query `?chat=<convId>`. Если пользователь хочет поресёрчить идеи, обсудить тренды или просто задать вопрос ассистенту — ему некуда писать, кроме как открыть фейковый пост-черновик. Это разрушает естественный флоу.

Backend уже умеет в множественные `workspaceConversations` (`createWorkspaceConversation`, `getWorkspaceConversations`, `sendWorkspaceMessage`) — то есть инфраструктура под полноценные диалоги есть, не используется только UI.

Ограничение: чат пока вспомогательный инструмент, а не кор-фича. Память по бренду, скиллы, агентные инструменты — отложено. Дизайн рассчитан на минимально жизнеспособный, но расширяемый формат.

## Решение верхнего уровня

Две независимые сущности, обе работают на одном и том же `workspaceConversations` API:

1. **Глобальный чат «Ассистент»** — новая страница `/app/assistant`, последний пункт в основной навигации сайдбара. Полноценный AI-ассистент по SMM: ресёрч идей, советы, brainstorm. История диалогов копится, привязана к workspace. **Без генерации картинок** (это эксклюзив редактора).
2. **Editor-чат** — остаётся в редакторе, но переводится в режим «scratch-pad»: всегда стартует пустым, в UI не восстанавливается. На бэке conversation создаётся как раньше. Получает кнопку явной очистки.

Связь между сущностями — один направленный мост: action-кнопка `open_in_editor` в глобал-чате создаёт пост-идею и кидает в редактор. Старый диалог остаётся в истории «Ассистент». Никакого «продолжения conversation» в редакторе — диалоги всегда независимы.

## Глобальный чат «Ассистент»

### Маршрут и сайдбар

- Путь: `/app/assistant`. Опциональный query `?conv=<id>` для глубокой ссылки и сохранения активного чата при F5.
- В `useAppLayout.ts` → `allItems` добавляется последним:
  ```ts
  { id: 'assistant', icon: 'sparkles', label: 'Ассистент', route: '/app/assistant' }
  ```
- Иконка `Sparkles` из `lucide-vue-next` (нужно зарегистрировать в `iconComponents` map в `AppSidebar.vue`).
- Доступно всем ролям воркспейса (включая viewer), без UI-гейта по тарифу. Backend сам отвечает 403, если что — frontend показывает обычный error-toast.

### Layout

Two-pane:

```
┌─ AppSidebar ─┬───────── активный чат ─────────┬──── история ────┐
│              │ ┌─ [+ Новый чат] ───────────┐ │ [🔍 Поиск...]   │
│ ...          │ │                            │ │                 │
│ Ассистент    │ │  user:    ...              │ │ • Idea 1        │
│              │ │  ai:      ...              │ │ • Brand x       │
│              │ │  [+ Идея][📝 В редактор]   │ │ • ...           │
│              │ │                            │ │                 │
│              │ └────────────────────────────┘ │                 │
│              │ ┌─ textarea + send ──────────┐ │                 │
└──────────────┴─└────────────────────────────┘─┴─────────────────┘
```

- **Главная секция**: max-width активного чата ~760px, центрирован. Сообщения через переиспользуемый `Message` из `lib-modules/conversations`. Под последним сообщением ассистента (если в нём были actions) — горизонтальный ряд `ActionCard`. Внизу — textarea с кнопкой отправки, поведение Enter/Shift-Enter — как в editor-чате.
- **Правая колонка** — фиксированная ширина ~260px, всегда видима. Поиск по названию (клиентский фильтр). Список диалогов сортируется по `updated_at` desc, активный подсвечен `bg-accent`. Контекстное меню через right-click / hover-trigger: переименовать, удалить.
- **На очень узких экранах** (`< lg`, ~1024px) правая колонка скрывается, в шапке появляется иконка `History`, открывает overlay-drawer.
- **Кнопка `+ Новый чат`** — над сообщениями (или возле заголовка). Сбрасывает текущий conversation, URL → `/app/assistant`.

### Empty states

- **Нет активного диалога** (новый чат / нет диалогов): центрированный hero-блок с заголовком («Чем поможет?») и 4 suggested-prompts кнопок:
  - «Дай 5 идей для рилса в нише [твоя ниша]»
  - «Что сейчас в трендах у [ниша]»
  - «Напиши хук для поста про…»
  - «Анализ моего бренда: с чего начать»

  Клик подставляет текст в textarea (без авто-отправки), фокус на textarea.
- **Нет выбранного workspace**: стандартный «Сначала выбери бренд», как в других страницах продукта.

### URL-поведение

- `/app/assistant` без query — открывает последний активный диалог из `localStorage` (per workspace), либо empty state.
- `/app/assistant?conv=<id>` — конкретный диалог.
- При создании нового сообщения в empty state — lazy создаём conversation (`createWorkspaceConversation`), `router.replace({ query: { conv: id } })`.

### Заголовок диалога

При первом обмене backend в SSE-стриме возвращает `set_title` (это уже работает в editor-чате). Сохраняем `title` в локальном store истории, обновляем item в правой колонке.

## Editor-чат: изменения

Не переделываем, чистим поведение.

### Что меняется

- **Старт всегда пустой.** В `EditorChatPanel.vue` на mount: `chatMessages = []`, `conversationId = null`. Снимаем восстановление из URL и из стора.
- **Query-param `?chat=<convId>` уходит.** Текущий код в `EditorChatPanel.vue:99-100` пишет его в URL — удаляем. URL поста чистый: `/app/editor?postId=<id>`.
- **Lazy create conversation остаётся.** Первое отправленное сообщение → `createWorkspaceConversation` → `setConversationId` локально (НЕ в URL). На бэке conversation сохраняется, но в UI это не подсвечивается.
- **Кнопка `Очистить` в шапке чат-панели.** Иконка `Eraser` (lucide). Клик → `chatMessages = []`, `conversationId = null`. Бэк не дёргаем — старый conversation остаётся в БД (для будущей analytics / ручной экспертизы).
- **Action-парсер вызывается, карточки не рендерятся.** Если модель вдруг вернула system-блок — режем хвост из текста (чтобы юзер не увидел маркер), но `actions[]` игнорируем (юзер уже в редакторе, кнопки `+ Идея` / `В редактор` не имеют смысла).

### Что НЕ меняется

- AttachMedia, генерация картинок (`imageGenerator`), prompt-improver, templates dropdown.
- Доступ для viewer (сохранён по коммиту `3215b66`).
- SSE-стрим, `set_title`, `response_end`, обработка ошибок.

### Точечная проверка в plan-фазе

- Используется ли `conversationId` из `useContentEditor` где-то ещё, кроме `EditorChatPanel`. Скорее всего нет, но перепроверить.
- Очистка зависимых стейтов на mount, чтобы при переключении между постами не «протекало» предыдущее (см. коммит `f0a3372` — там уже была похожая чистка на смену workspace).

## Action-протокол

### Формат

В хвосте сообщения ассистента (после основного markdown-ответа):

```
<обычный markdown-ответ>

========SYSTEM======
{ "actions": [
  { "type": "save_as_idea", "title": "Bold-цвет помада", "description": "Идея для рилса: ..." },
  { "type": "open_in_editor", "title": "...", "description": "..." }
] }
```

Один блок на сообщение. Внутри — массив (даже из одного элемента — единообразный протокол). Если actions нет — модель просто не пишет маркер.

### Типы actions (v1)

- `save_as_idea` → создаёт пост со статусом «идея» в календаре с переданными `title` + `description`. Toast «Идея сохранена в календаре» с CTA «Открыть». Юзер остаётся в чате.
- `open_in_editor` → создаёт пост-идею + `router.push('/app/editor?postId=<id>')`. Editor-чат стартует пустым, idea отображается в редакторе через `posts/get(id)`.

### Системный промпт (на старте — фронт)

Захардкоженная инструкция, которая дописывается к conversation на стороне фронта (или, если бэк не позволяет — фиксируется как требование к бэку добавить в дефолтный system_prompt):

> «Когда в обсуждении появляется конкретная идея для поста (тема + общее описание), в конце ответа добавь блок:
> `========SYSTEM======{"actions": [{"type": "save_as_idea", "title": "...", "description": "..."}]}`
> Допустимые типы: `save_as_idea`, `open_in_editor`. Можно вернуть массив (несколько идей за раз). Если идеи нет — блок не пиши.»

Когда логика мигрирует на бэк — этот текст уезжает в backend system_prompt, фронт просто парсит ответ.

### Парсинг

Живёт в `lib-modules/assistant/helpers/actionsParser.ts` (общая утилита, переиспользуется editor-чатом для скрытия хвоста).

- Стримим текст в `Message` как обычно.
- Во время стрима в `appendToChatMessage`: как только в накопленном тексте встречается подстрока `\n========SYSTEM======` — переключаемся в режим «копим в hidden buffer». Текст до маркера остаётся видимым, последующие чанки в видимый текст не уходят.
- После `response_end` парсим hidden buffer как JSON. При успехе — `message.actions = parsed.actions`. При битом JSON — `actions = []`, текст в чате остаётся обрезанным (юзер не видит мусор).
- Опциональный длинный токен на случай ложных срабатываний: при необходимости в plan-фазе сменить на `<<<WRITELO_ACTIONS>>>` или подобный.

### UI: ActionCard

Под `Message` (когда `message.actions.length > 0`) — горизонтальный ряд карточек. Каждая:

- `title` крупно, `description` приглушённо (line-clamp 2).
- Одна основная кнопка справа, label — по `type`:
  - `save_as_idea` → `[+ Идея]`. Клик → API создания поста-идеи → toast.
  - `open_in_editor` → `[📝 В редактор]`. Клик → создание + `router.push`.
- После клика — кнопка превращается в пассивную ссылку `✓ Сохранено: "Title" →` (по клику открывает идею в календаре/редакторе). Двойного создания не делаем.

Несколько идей в одном ответе («дай 5 идей») = массив `actions` → 5 карточек подряд.

## Зависимости от бэка

Фиксируем как требования (plan-фаза проверит спеку `docs/v1-28.04.json` и при необходимости откроет тикеты бэку).

1. **Создание поста со статусом «идея»** через существующий `createWorkspacePost` (или эквивалент). Если такого статуса нет — блокер для бэка, перед фронт-имплементацией нужно согласовать.
2. **Возможность дописать кастомную system-инструкцию** в `sendWorkspaceMessage` или иметь её зашитой в дефолтный system_prompt бэка. Если фронт не может дописать — поговорить с бэком, добавить инструкцию в дефолт. План-фаза проверит контракт.

## Скоуп

### В скоупе

- Новый модуль `lib-modules/assistant/` — страница, two-pane layout, store истории диалогов, action-парсер, `ActionCard`.
- Маршрут `/app/assistant`, новый item в сайдбаре, иконка `Sparkles`.
- Парсер system-блока — общая утилита, потом переедет в backend.
- Системный-промпт инструкция (захардкожена на фронте на старте).
- Editor-чат: scratch-режим (всегда пустой старт), кнопка `Очистить`, удаление `?chat=` из URL, парсер вызывается без рендера actions.

### Сознательно НЕ делаем (YAGNI)

- Память по бренду / per-workspace knowledge base.
- Custom skills, агентные инструменты в чате.
- Слэш-команды (`/idea`, `/analyze`).
- Action-типы кроме двух (`analyze_reel`, `find_trends`, `find_competitors`, …) — переедут с бэком.
- Шаринг диалога между членами команды (даже если business-план).
- Экспорт / печать диалога.
- Цитирование / ответ на конкретное сообщение.
- Регенерация ответа (как ChatGPT «Regenerate»).
- Смена модели в UI.
- Server-side full-text search по диалогам — на старте клиентский фильтр.
- Recovery editor-чата при возврате к посту — вечная амнезия в UI.

## Риски и mitigation

- **AI игнорирует формат / шлёт битый JSON.** Парсер failsafe-ит: маркер всегда режем из текста, при битом JSON `actions = []`. Юзер видит чистый ответ без кнопок.
- **Маркер `========SYSTEM======` встречается в ответе естественно.** Маловероятно, но используем достаточно длинный токен; в plan-фазе можно подкрутить (например, `<<<WRITELO_ACTIONS>>>`).
- **Юзер закрыл вкладку посреди стрима.** Восстановления частично-пришедших сообщений не делаем. Чат восстанавливается только из `?conv=<id>` или `localStorage` last-active.
- **Длинные диалоги, scroll-производительность.** Не паримся на старте; при необходимости — virtualised scroll.

```
│   └── index.ts                  # Action, AssistantMessage типы
└── index.ts                      # public API
```
